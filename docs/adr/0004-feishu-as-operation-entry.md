# ADR-0004：飞书从「登录渠道」升级为「操作入口」

- **状态**：已接受
- **日期**：2026-11-22
- **决策者**：nicknicka

## 背景

阶段 3 之后，业务纵深（客户 → 商机 → 报价 → 合同 → 订单 → 回款）已经完整，但飞书集成只停留在两处：

1. **OAuth 登录**——飞书只是「怎么进来」，不是「进来做什么」；
2. **单向通知卡片**——`im.message.receive_v1` 事件处理器只打结构化日志，不回复、不落库；发出去的卡片是 `defaultCard`（标题 + 一段文字），没有按钮。

结果是飞书在系统里可有可无：删掉飞书集成，CRM 功能一个不少。同时业务侧「很素」的抱怨也指向同一个问题——只有 CRUD 表单，没有能让销售少做一步的自动化。

本 ADR 记录把飞书改造成**真正的操作入口**的决策：机器人与交互卡片承担日常动作，网页端退回「看全局、做配置、处理例外」。

## 决策

### 1. 机器人的职责边界：只做「一句话 → 一条结构化跟进」

`@机器人 客户杭州云启今天电话聊了，预算80万，下周三要方案` 的处理链路：

| 步骤     | 实现                                                  | 失败时                                       |
| -------- | ----------------------------------------------------- | -------------------------------------------- |
| 去重     | `FeishuMessageLog.messageId` 主键抢占                 | 重复推送直接丢弃                             |
| 身份映射 | `open_id` → `User`                                    | 回「账号未绑定」卡片，不做任何业务动作       |
| 理解     | 模型解析成 JSON（客户、方式、摘要、下一步时间、金额） | 退回关键词规则解析，卡片标注「按关键词识别」 |
| 客户匹配 | **代码**在候选列表里做归一化匹配                      | 匹配不到或命中多个 → 回追问卡片，绝不硬写    |
| 落库     | 复用 `createFollowUp`（同一套权限校验）               | 回失败原因                                   |
| 回复     | `followUpCreatedCard`，带「打开档案 / 再记一条」按钮  | 只记日志，不回滚业务结果                     |

**关键原则：模型只负责理解，不负责决定。** 模型输出被限制为 JSON，客户匹配、权限判定、写入规则全在代码里。所以模型胡说时最坏结果是「没记上并追问用户」，不会产生脏数据。

### 2. 卡片按钮直接写业务数据（这是飞书原生做不到的）

已实现的三种交互：

| 卡片     | 按钮               | 回调动作                       | 数据变化                                       |
| -------- | ------------------ | ------------------------------ | ---------------------------------------------- |
| 公海客户 | 我来认领           | `claim_customer`               | 写 `Customer.ownerId`，卡片换成「已被认领」    |
| 商机阶段 | 推进到「下一阶段」 | `advance_opportunity_stage`    | 写 `Opportunity.stage`，卡片标题与按钮同步刷新 |
| 追问卡片 | 选客户名           | `create_followup_for_customer` | 把原始那段话落成该客户的跟进                   |

技术上是 `card.action.trigger` 回调 + `channel.updateCard()` 原地刷新。**刷新而不是再发新消息**，避免刷屏；刷新失败时退化为发一张结果卡片。

**安全前提：按钮 `value` 是客户端回传的，一律视为不可信输入。** 每个动作都重新查库、按当前用户权限校验，并校验「目标阶段是否恰好是下一步」，防止跳级或越权改他人客户。

### 3. 模型配置放在设置页，走 OpenAI 兼容协议

- 单条生效配置（`ModelConfig`），保存时在事务内把旧配置置为不启用；
- `apiKey` 用 AES-256-GCM 加密入库，密钥由 `SESSION_SECRET` 加用途后缀派生（不新增环境变量）；页面只返回掩码；
- 「保存即测试」：保存后立即调一次极小请求，把结果与耗时写回配置并在页面展示；
- 提供 DeepSeek / OpenAI / 通义千问 / 智谱的预填，降低配置门槛；
- 只有管理员可读写（`requireAdmin` 在 action 内部，不依赖页面隐藏）。

### 4. 首页改为「飞书工作台」

概览页第一屏回答「飞书干了什么」：机器人处理消息数、落成跟进数、主动追问数、卡片完成操作数，以及最近活动时间线。业务数字退居第二屏。管理员还能看到「哪些同事的飞书身份没绑定」——这是机器人能不能用的前提条件，属于可执行的待办而非装饰。

### 5. 权限唯一来源不变

飞书侧的每一次写入都先映射成 `CurrentUser`，再走与网页端完全相同的 `accessScopeFor` / `ownerWhere` / repository 函数。**不为飞书另设一套权限逻辑**，也不信任飞书事件里的任何角色信息。

## 影响

- **正面**：销售不必打开网页即可记录跟进、推进阶段、认领客户；网页端角色变成「看全局 + 做配置 + 处理例外」；「飞书和这个项目什么关系」有了可演示的答案；模型可替换，不绑定单一服务商。
- **负面**：引入模型调用意味着额外的延迟与成本，且解析质量依赖模型（用规则兜底缓解）；卡片 JSON 与回调格式受飞书开放平台版本影响，需要回归测试；新增四张表（`model_configs`、`chat_bindings`、`feishu_message_logs`、`card_action_logs`）。
- **运维前置**：需在开放平台添加机器人能力并发布版本（否则报 `230006 Bot ability is not activated`），并订阅 `im.message.receive_v1` 事件与 `card.action.trigger` 回调。属后台操作，非代码变更。

## 替代方案

- **只发通知卡片（现状）**：零风险但无价值，用户仍要回网页操作，故不选。
- **让模型直接决定写哪个客户、什么阶段**：省掉匹配代码，但一旦幻觉就会写脏数据且难以追责，故不选；改为模型只输出候选名、代码做匹配。
- **卡片按钮跳转到网页完成操作**：实现最简单，但用户仍需离开飞书，丢掉了「在飞书里把事情做完」的核心价值，故不选。
- **把模型 Key 放环境变量**：运维更简单，但管理员无法自助更换服务商，也无法在界面上测试连通性，故不选。
- **为飞书单独实现一套写入逻辑**：可以少一次身份映射，但会产生第二套权限实现，长期维护成本更高，故不选。

## 补充（第二期）：从「被动回答」到「主动催办」

第一期只解决了「销售想说的时候能说」，但销售不会主动想起来去查系统。第二期补上系统侧驱动：

### 6. 提醒按「负责人 × 类别」聚合，不按对象逐条发

三类信号：**跟进超期**（登记的下一步时间已过且之后没再跟进）、**客户沉默**（超过 14 天无跟进）、**待回款**（订单金额减已登记回款大于 0）。

聚合规则是刻意的：一个负责人有 20 个沉默客户时，发 20 条消息只会让他把机器人设为免打扰。所以同类合并成一张卡片、最多列 5 条明细、其余提示「见网页端」。但跨类别不合并——催电话和催欠款的下一步动作不同，混在一起反而看不清。

去重细节：同一客户有多条超期记录时只提醒一次；如果该客户之后又有新跟进，视为已处理，不再提醒。

### 7. 扫描与推送分离

`scanReminders()` 纯只读，`dispatchReminders()` 才发消息。这样网页端可以「先看再推」（管理员点「立即推送到飞书」），定时任务可以「扫完就推」（`POST /api/cron/reminders`），两条路径共用同一份数据，不会出现两套逻辑各说各话。

### 8. cron 鉴权抽成公共模块

两个 cron 端点（`sync-contacts` / `reminders`）共用 `src/lib/cron/auth.ts`。抽出来是因为重复实现容易在某一处漏掉 fail-closed——未配置 `CRON_SECRET` 时必须拒绝执行，而不是「没配置就放行」。

### 9. 群绑定不提升权限（重申）

`ChatBinding` 让「在这个群里说『今天聊了』」能自动带出客户名，省掉每次念公司名。但它只是**一条记忆，不是权限凭据**：解析时会再核对当前用户是否本来就能看到该客户，看不到则等同没有绑定，机器人照常追问。

### 10. 提醒的可达性要显式暴露

未绑定飞书的负责人收不到任何提醒——这是提醒功能最隐蔽的失败模式（系统显示「已推送」，人却什么都没收到）。所以待办页每条提醒标注「飞书已绑定 / 收不到卡片」，首页横幅也直接写出「N 类因负责人未绑定飞书发不出去」。
